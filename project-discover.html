Project Overview

The Discover Partner Reporting platform underwent a 4-phase architectural transformation over several years, evolving from a fragile relational backend into a high-performance cloud lakehouse and eventually a next-generation SaaS Microsoft Fabric AI engine. This ETL pipeline and Lakehouse architecture supports three Power BI semantic models, each designed and optimized for different reporting and analytical use cases, collectively powering 150+ report pages.

  • SI (System Integrator) Reports
  • ISV (Independent Software Vendor) Reports
  • PPT (PowerPoint) Reports — Used to generate PowerPoint pages

Phase 1 — Foundations & Legacy Stored Procedure Engine

April 2022 to October 2023

Architecture

The initial implementation was constructed around Microsoft Dataverse as the primary operational source. Data synchronization was handled via Power Automate flows that pushed records directly into an Azure SQL Server relational database (Bronze layer schema). Within SQL Server, complex transformations were executed using nested stored procedures, and views were created to support silver and gold layers. Reports were delivered via Power BI import mode with Power BI Embedded (A capacity) over a web app with AD authentication.

Under this architecture the team delivered around 20–25 Power BI report pages.

Bottlenecks Identified

  • Power Automate flows frequently failed, skipped triggers, or suffered heavy delays when more than a few record updates hit Dataverse within a 30-second window
  • Backend ETL stored procedure syncs took over one hour to execute
  • Power BI report refreshes took over 10 minutes, limiting total backend and frontend sync to a 3-hour interval

Phase 2 — Cloud Modernization to Databricks Lakehouse

November 2023 to September 2024

Architecture

To resolve persistent flow failures and long ETL windows, a modern Lakehouse architecture was architected, proven via POC, and deployed to production:

  • Azure Synapse Link replaced Power Automate flows, syncing Dataverse tables into Synapse Lake databases in near-real-time — eliminating 100% of previous flow trigger failures
  • Databricks PySpark/Scala notebooks extracted tables from Synapse Lake via serverless SQL endpoints and performed scalable transformations, building clean Silver and Gold Lakehouse layers
  • The data model was refactored into a Snowflake Schema, removing redundant attributes to drastically speed up report querying

Results

  • Backend sync and Power BI refresh reduced from 3 hours to 30 minutes (6× faster)
  • Monthly cloud spend reduced from £7,000 to £2,500/month — a 64% cost reduction
  • 100% elimination of pipeline sync failures

Bottleneck at Scale

After a year in production, the main report file expanded to over 0.5 GB with 75+ complex pages, and the primary fact table grew from 1 million to over 10 million rows, causing Power BI Embedded capacity degradation.

Phase 3 — Migration to Microsoft Fabric Platform

October 2024 to June 2025

Architecture

  • Fabric Link mirrored Dataverse tables into Fabric Lakehouse (Bronze Layer) in near-real-time
  • Fabric PySpark/Scala notebooks executed multi-stage transformations orchestrated within centralized Fabric pipelines using DAG (Directed Acyclic Graph) notebook activities
  • Single-location orchestration with automated error logging, native Git workspace integration, and automated CI/CD deployment pipelines (Dev → UAT → Prod) with dynamic semantic model parameterization
  • Azure DevOps for source code management; Fabric Deployment Pipelines for environment promotion

Results

  • Processing speed doubled on F32 capacity
  • Report load times accelerated significantly
  • Operating costs remained flat despite 10× data volume growth
  • Platform scaled to 10M+ fact-table rows and 40+ new report pages

Phase 4 — Cost Reduction & Model Optimizations

July 2025 to Present

Architecture

With increased concurrent embed users, the infrastructure was upgraded to F64 Fabric Capacity based on Fabric Capacity Metrics App analysis. Key optimizations:

  • Compute separation: Heavy, resource-intensive pipelines migrated to Databricks managed clusters; lightweight pipelines moved to Databricks serverless compute — avoiding Fabric shared capacity consumption for Spark workloads
  • Incremental refreshes: Custom Databricks scripts implemented incremental processing for fact tables in Power BI semantic models — only newly added or modified data is processed, significantly reducing refresh costs
  • Copilot Studio AI agents integrated to automate dataset deliveries to partner users, eliminating manual report generation and distribution
  • Databricks Genie POC built and embedded into a custom Flask/JavaScript/HTML web app for conversational analytics

Results

  • 50% additional reduction in overall platform cost
  • Greater flexibility to scale compute independently of shared Fabric capacity
  • AI-assisted partner reporting via Copilot Studio at no net cost increase

Phase 5 — Conversational Analytics POC (Fabric Data Agents & Databricks Genie)

March 2026 to Present

Evaluation

Led a head-to-head evaluation of two AI-assisted analytics options using the same data domain and benchmark questions:

PlatformData SourcesEmbeddingOutcome
Fabric Data AgentFabric Lakehouse + Power BI semantic modelLimited to Fabric ecosystemEvaluated, not selected
Databricks GenieGold-layer Unity Catalog tablesEmbeds into Flask web appSelected

Databricks Genie was selected because it fit best with the Databricks-based processing layer from Phase 4, kept workloads off the shared Fabric capacity, and could be embedded directly into the existing Flask web application.

Genie Implementation (Dev Environment)

  • Data sources: Curated Gold-layer fact and dimension tables from Unity Catalog; table/column descriptions added, irrelevant fields hidden
  • Relationships: Primary/foreign key joins configured between fact and dimension tables (snowflake schema) for correct multi-table joins
  • Instructions: Domain-specific business definitions, KPI logic, default filters, date/fiscal period handling, and business synonyms
  • Sample SQL queries: Parameterised examples for most common and complex questions — multi-join aggregations, period-over-period comparisons
  • Testing: Benchmark set of real business questions with expected SQL; iteratively refined descriptions and examples
